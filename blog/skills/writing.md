## §2. 記事構成テンプレート

### ガジェット・ツール・AI・アプリ記事
1. 引き込む導入文（冒頭3行で読者を離さない）
2. ツール・方法の紹介（名前・価格・概要）
3. リサーチ・口コミのサマリー（複数源から）
4. キャラクター対話を交えた解説
5. 生産技術視点での評価（4軸で）
6. 金額換算セクション（年間削減金額・回収期間を必ず記載）
7. 実際に使ってみた感想・数値
8. 深みのある考察（WHYの2段階・逆説・業界への問い）
9. 結論（どんな人に向くか・お得度の総括・一言締め）

### 裏話・工場実態記事
1. 引き込む導入（裏話型・共感型）
2. 具体的なエピソード（リアルさが命）
3. キャラクター対話
4. 「実はこれ、日常にも使える」という橋渡し
5. 関連するガジェット・ツールへの自然な流れ
6. 読者への問いかけで締める

## §3. ガジェット・ツール評価の4軸（必須）

1. **時短効果** ── 作業時間をどれだけ削れるか（分・時間で示す）
2. **効率化** ── 工程・手順をどう改善するか
3. **費用対効果** ── 金額換算で元が取れるか・いつ取れるか
4. **再現性** ── 誰でも同じ恩恵を受けられるか

## §4. 金額換算の公式（必ず盛り込む）

```
時給 × 削減できる時間（日） × 年間稼働日 = 年間削減金額
年間削減金額 ÷ 価格（または月額×12） = 回収期間
```

- 読者の時給は **「950円」（全国で最も低い都道府県の最低賃金水準・2025年時点）** を標準として計算。理由：最も生活が苦しい時給帯の人でも元が取れることを保証し、「誰が買っても損しない」を実証するため。時給がこれより高い人はボーナス回収となる
- 数字は必ず3つセットで語る：価格・削減時間・年間換算金額
- 比較対象を明示する：「これを使わない場合、年間〇時間をムダにしている」

### 🔴【最重要・絶対遵守】ROI計算根拠の明記ルール

**当ブログの最大の売りは「投資対効果を金額で可視化する力」。  
数字を出すだけでなく "なぜその数字になるのか" の計算過程を必ず記事内に明示する。**

#### 必須セクション「📐 ガジェット投資対効果（ROI）」

すべてのレビュー記事に**必ず**専用セクションを設け、以下3要素の計算式と数値を **table で明示**する：

1. **1日あたりコスト** = 購入価格 ÷ 想定使用日数
   - 表記例：`45,000円 ÷ 1,600日 = 28円/日`
2. **節約価値の根拠** = 節約時間 × 時給(950円/h標準・最低賃金基準)
   - 「なぜその節約時間か」の根拠を必ず1段落で説明
   - 表記例：`10分/日 × 15.83円/分（時給950円換算）= 158円/日`
3. **損益分岐点** = 投資金額 ÷ 1日節約価値
   - 表記例：`45,000円 ÷ 333円/日 = 135日 ≒ 4.5ヶ月`
4. **長期累計価値**（任意） = 節約価値/日 × 使用日数
   - 表記例：`333円 × 1,600日 = 53.3万円`

#### 仮定（％・時間など）の根拠説明 必須

「効率3%向上」「時短10分」など仮定の数字を出すときは、**そう仮定した理由を必ず明記**する。

❌ NG：「効率が3%向上」（根拠なし）
✅ OK：「ショートカット8つの操作時間が1.2秒→0.4秒、1日100回操作で80秒/8時間=0.28%、これに疲労軽減・腱鞘炎リスク低減を加味して保守的に3%」

#### 記事完成チェックリスト（公開前に必ず確認）

- [ ] ROI専用セクション（h2）が存在するか
- [ ] 1日あたりコストの計算式が明記されているか
- [ ] 節約時間/効率向上率の**根拠説明**があるか
- [ ] 損益分岐点の日数/月数が明示されているか
- [ ] 全数値が「式 = 結果」のtable形式で示されているか
- [ ] 時給は950円（全国最低賃金水準）を標準として計算しているか
- [ ] **本文に `***` `**` `*` の Markdown 残骸が残っていないか**（必ず getComputedStyle またはcurl/regex で確認）

## §5. 導入文の型（冒頭3行で必ずどれかを使う）

- **問いかけ型**：「1日30分、何もしないのに消えている時間があるとしたら？」
- **数字衝撃型**：「年間125時間。それがこのツールを使わない人が失っている時間だ」
- **共感型**：「工場で働いていた頃、僕は毎日同じムダな作業を繰り返していた」
- **逆説型**：「効率化ツールを買いすぎると、逆に非効率になる」
- **裏話型**：「工場では絶対に教えてくれない、時短の本当の話をする」
- **口コミ型**：「Amazonに1,000件以上のレビューがある。その星1を全部読んだ」

## §6. キャラクター対話ルール

```
【タナカ】「〜〜〜（ボケ・勘違い・素朴な疑問）」
【オオタニ所長】「〜〜〜（ツッコミ＋深みのある一言）」
```

- 1記事2〜3箇所で挿入（難しい内容・裏話・金額換算の場面で効果的）
- タナカ：知識は浅いが素直で憎めない（急に賢くなるNG）
- オオタニ所長：生産技術の現場経験を持つ語り手（一人称は「僕」または「私」）
- **1セリフ＝1メッセージ**（詰め込みすぎNG）
- メタ表現禁止（「読者さんへの〜」など）
- **語調を絶対に変えない**（オオタニは断言口調、タナカは敬語口調）
- 🔴 **記事の冒頭を吹き出しで始めない**（2026-07-29制定）。名乗りも文脈もないままキャラが結論を言い渡す形になり、読者には「いきなり偉そう」に映る。**順序は「挨拶・導入文 → 3行まとめ → 吹き出し」**。吹き出しは読者が状況を把握したあとの補足・掛け合いに使う
- 🔴 **本文は必ず導入文（段落/引用・40字以上）から始める**（2026-07-29制定）。**目次(RTOC)は最初のh2の直前に自動挿入される**ため、h2で書き出すと**アイキャッチの直後にいきなり目次**が出て「メニューから始まる記事」になる。点検は `python3 blog/scripts/check_article_head.py`（最初のh2より前に導入ブロックがあるか全記事チェック）
- 🔴 **相手が誰かで語尾を変える**（2026-07-29制定）
  - **タナカ相手**（掛け合い）＝常体でOK。ただし**見下しは禁止**（「甘いな」「君にはまだ分からんようだな」「だから損してたんだ」はNG）
  - **読者に直接向けるセリフ**＝**必ず敬体**（です・ます）。「結論から言う。〜ことだ」ではなく「結論からお伝えすると、〜です」

## §14. 深みと説得力を出す技術

- WHYを2段階掘り下げる（表面→1段階→2段階）
- 逆説を使う：「安いガジェットほど高くつく理由」
- 現場の失敗談・成功談を入れる
- 結論を先に言い切る：「**結論からお伝えすると、これは買いです**」（自信を持って言い切ってよいが、読者への言い渡しにしない。旧例「結論から言う。このツールは買いだ」は**上から目線に読まれるため廃止**／2026-07-29）
- 読者の反論を先に潰す：「高いと感じる人もいるかもしれません。でも…」

## §14-b. 依頼文の定型（2026-07-29制定・リベシティ合宿の知見を反映）

記事作業をAIに頼むときの型。**どれも「一文足すだけ」で結果が目に見えて変わる**ので省略しない。

### ① 既存記事を直すとき ── 「どこを変えたか」を必ず言わせる
```
（直してほしい内容）
修正した箇所については、どこをどう修正したかを教えて欲しい。
```
> **なぜ**：そのまま編集してくれるのはありがたいが、**どこが変わったのか把握できないまま公開してしまう**のがいちばん危ない。差分を言わせてから採否を判断する。
> 記事が多いときは「**◯◯の中から、直した方がよいと思われる記事を1つ選んで**」と**対象を1件に絞らせる**（全記事の改善案が一度に出ると処理しきれない）。

### ② 記事テーマを出させるとき ── 先に逆質問させる
```
次の記事を書きたいので、テーマを5つ出してほしい。
テーマを出すにあたり、確認したいことはヒアリングして欲しい。
```
> **なぜ**：いきなり案を出させると当たり障りのないテーマが並ぶ。**先に質問させると、自分でも言語化できていなかったネタが引き出される**。

### ③ 新記事を書かせるとき ── 4点セットで指示する
```
（テーマ）に沿って記事を書いて欲しい。
記事を書くにあたり、私が実践している（内容）を先にヒアリングしてから書き始めて欲しい。
この時に、ヒアリングした内容以外のことを予想で書かないこと。
文字数は◯◯字程度。この記事の目的は「（誰に何を持ち帰ってもらうか）」。
```
> **なぜ**：①ヒアリング ②予想で書かせない ③文字数 ④**記事の目的**。特に④は「人間と同じで、何のために書くか分かると書き方が変わる」ため毎回入れる。②は §16 の最重要禁止事項（体験の創作）を発生源で止めるための一文。

1. **企画レビュー** ── テーマ・キーワード・構成案をユーザーに確認
2. **記事レビュー** ── 完成記事の最終確認・修正
3. **改善レビュー** ── 公開後の分析結果の共有

## §16. 禁止事項

- 「便利です」「時短になります」だけで金額換算しない記述
- 根拠のない誇張（「神ツール」「最強」など）
- 口コミの直接引用・コピペ
- 現場経験のない薄い表現（「便利そうです」など）
- キーワードの不自然な詰め込み
- 振り返りレポートの省略
- キャラクターの語調変更
- 🔴🔴 **やっていない体験を、やったかのように書くこと（2026-07-29制定・最重要）**。AIに記事を書かせると**実際には使っていない機能・行っていない検証・持っていない製品の使用感を、自然な文章で創作してしまう**。当ブログは実機レビューが売りなので、これが起きた瞬間に信頼が消える。
  - **防ぎ方（執筆指示に必ず入れる3点セット）**：①**先にヒアリングさせる**（「記事を書くにあたり、私が実践している◯◯を先にヒアリングしてから書き始めて欲しい」）②**「ヒアリングした内容以外のことを予想で書かないこと」と明記**する ③**新しい製品・マイナーな製品は自分から情報を与える**（AIの学習範囲外だと平気で捏造する）
  - **書いてよいのは**：自分が実際に測った数値／実際に撮った写真から言えること／公式サイトで裏取りした仕様／「一般にこう言われている」と出典付きで示せること
  - **書いてはいけないのは**：使っていない機能の使用感／していない比較の結論／「◯週間使ったが」という未経験の期間表現／体験談風の創作エピソード
  - 参考：リベシティ合宿（2026-06-04）で講師が自身の失敗として「実際にやったことのないことを、やったかのように書かれた。ブログの信頼性がなくなる」と警告していた事例と同種。当ブログでも2026-07-26に**記事552のアダプタASINが実機と別商品**という形で発生済み
- 🔴 **読者に偉そうな態度をとること（2026-07-29制定・例外なし）**。自信のある結論＝ドヤ顔は歓迎するが、**読者を下に置く表現は絶対に書かない**
  - NG：命令形（「やってみろ」「回収していけ」「数えろ」）／詰問（「誰がそう決めた？」）／見下し（「甘いな」「知らないと損」「素人は」）／言い渡し（「結論から言う。」「言っておく」「教えてやる」）／読者への「〜すべきだ」
  - OK：「結論からお伝えすると〜です」「一度数えてみてほしい」「〜が向いています」「〜をおすすめしたい」
  - 判定基準：**そのセリフを"初対面のお客さん"に face-to-face で言えるか**。言えないなら書かない

### 記事修正からの学習（3段昇格・2026-05-31新設）
記事を修正したら **必ず `edit_logger.py` で生ログを残す**（git diff だけでは「なぜ直したか」が残らないため）。
```
python3 blog/scripts/edit_logger.py --slug <slug> --reason "<理由>" --learning "<学び>" --tag <種別>
```
- ① 生ログ = `blog/edits/_log.md`（粒度細かい）
- ② 同じ種別タグが2回以上 → `blog/MEMORY.md`「失敗パターン」表 or「進化ログ」へ昇格（edit_logger が警告を出す）
- ③ 全社普遍ルール → `CLAUDE.md` / 本SKILL.md へ昇格
- 昇格済みルールは `~/.claude/projects/.../memory/feedback_blog.md`（執筆前に参照）
- 🔴 **④ 機械で検出できる失敗は `article_lint.py` にチェックを追加する（2026-08-01新設・最終形）**。
  ルールを文章（SKILL/MEMORY）に書くだけでは読み忘れで再発する。同じ失敗が2回起きたら
  「文章のルール化」と同時に「lintのチェック化」まで行い、**publish_article.py が公開時に自動で止める**状態にする。
  価格割れ・偉そう表現・PR表記順序・冒頭構造・markdown残骸は昇格済み（初回実走で公開中3記事から残骸6件を検出→即修正した実績）

### ローカルプレビュー（実物を見ながら修正・2026-05-31新設）
記事の見た目（吹き出し・水色下線・ROIテーブル・画像）を本番JIN:R風に即確認できる。
```
python3 blog/scripts/preview_server.py   # → http://localhost:8794/preview/<slug>
```
mdを直してブラウザ自動リロード（WP往復なし）。装飾修正・画像配置の確認に使う。

## 🔁 記事推敲→公開の標準ルーチン（2026-06-02 確立・公開前必須）

「素材集めから本番公開まで」一気通貫の標準フロー。新記事・既存記事の改稿どちらにも適用する。

```
《準備フェーズ：記事めし》
⓪-a 素材収集(撮影/スクショ) → ⓪-b PROMPT.md生成 → ⓪-c context.md化
《制作フェーズ》
①執筆 → ②プレビュー起動 → ③画面を見ながら推敲 → ④事実確認 → ⑤修正ログ
→ ⑥アフィリリンク → ⑦ドライラン点検 → ⑧本番反映 → ⑨本番検証 → ⑩仕上げ
```

| # | 工程 | 具体アクション |
|---|---|---|
| ⓪-a | レビュー画像づくり（記事の土台＝素材） | 記事の土台となるレビュー画像（撮影写真のトリミング/背景クリーンアップ/注釈・図解・スクショ等）を用意し、記事めしPWA（`blog-capture-secure.gp6sk1029.workers.dev`・Cloudflare Access必須）でGoogle Driveフォルダにアップロード。**Codex経路**：先に保存先の記事フォルダを選択→プロンプト準備→「🧠 Codexで画像生成」→Codex側で送信1回→生成後「📥 Codex画像をDriveへ保存」。初回だけワークスペースを選ぶと、PWAが`.article-meshi-codex`を一時受け渡し用に自動作成する（パス入力不要）。完成画像は取込と同時にジョブ開始時のGoogle Drive記事フォルダへ直接保存する（記事を途中で切り替えても保存先を変えない）。**Canvaは必須ではなく、ユーザーが必要と判断した場合のみ仕上げに使う**。ChatGPT/Gemini手動経路とクリップボード貼付/ドラッグ&ドロップも残す。この画像群が記事の「画像の土台」になる |
| ⓪-b | 伝えたいこと＝記事の骨子・流れ（PROMPT.md） | PWAで「記事タイプ」＋「読者に伝えたいポイント（＝記事でポイントになること・話の流れ／優先度順）」を入力 → Driveの画像フォルダに `PROMPT.md` が自動生成される。これが**記事の骨子（伝えたいこと・流れ）の土台**になる |
| ⓪-c | context.md化（執筆セッション） | `python3 blog/scripts/article_from_meshi.py --folder-id <Driveフォルダid> --slug <slug>` → PROMPT.md取得＋画像を役割タグ(eyecatch/hero/section/product/diagram/compare/ngsummary)で分類し `articles/{slug}_context.md` を生成。**Claudeはこの context.md を最初に読む** |
| ① | 執筆 | context.md を基にmdを `blog/articles/` に作成。**記事めしメモは「種」、本文は深掘り**（MEMORY「記事めしメモは種」原則：各ポイントを仕組み/数値/理論/反論先回り/実体験で800〜1500字に展開）。前回記事スタイル踏襲・ROI table/キャラ対話/金額換算は必須 |
| ② | プレビュー起動 | `python3 blog/scripts/preview_server.py` → **Codexアプリ内ブラウザを表示して** `http://localhost:8794/preview/<slug>` を開く。ユーザーはCodexの横で本番風の見た目を確認する |
| ③ | 推敲ループ | ユーザーが横に表示した画面を見て指示 → 原稿を修正 → 自動リロード。気が済むまで往復 |
| ④ | 事実確認 | スペック・価格・設定範囲・対応規格は**公式 or 実機アプリで裏取り**。シリーズ品はモデルごと確認（例：ロックLiteはセンサー非搭載・タイマー式）。実機所有ユーザーの入力は正とする |
| ⑤ | 修正ログ | 修正のたびに `edit_logger.py --slug --reason --learning --tag`。同タグ2回で MEMORY/`feedback_blog.md` へ昇格 |
| ⑥ | アフィリリンク（**`:::product`カード標準**） | **下記「💰 アフィリエイト掲載の標準」に完全準拠**。要点：主役商品は `:::product` カード（Amazon＋楽天の2ボタン横並び＋公式商品画像）で掲載／Amazonは `?tag=gp6sk1029-22`／楽天は affiliate.rakuten.co.jp で商品リンク生成／画像は**レビュー対象ASIN一致の公式画像**（楽天メイン画像は別商品のことがあり要目視）／**PR表記（Amazon＋楽天を明記）必須**／WP公開版は `rel="sponsored nofollow noopener"` 自動付与。純正がAmazonに無い消耗品は信頼ブランドで代替（ユーザー選択） |
| ⑦ | ドライラン点検（**公開前必須**） | `python3 blog/scripts/publish_article.py --slug <slug>`（ドライラン）を実行すると `validate_blocks()`＋**`article_lint.py` 統合ゲート**が自動で走る：冒頭構造／偉そう表現／PR表記の位置／markdown残骸／表情記法露出／価格割れ疑い／カード位置。**ERRORが1件でもあると ⑧ の実投稿は自動でブロックされる**（回避 `--skip-lint` は原則禁止・使用時は理由をMEMORYへ）。未所有商品の記事は `--unowned` を付けて体験創作ワードも検査。低画質素材slot不使用（例：`新人タナカ ドヤ顔.png`=slot10は使わずニヤ顔=slot9/驚き=slot7）は従来どおり目視 |

| ⑨ | 本番検証 | `curl https://www.ootanisatan.com/<slug>/` を grep：新タイトル有/旧残骸0/アフィリタグ有/事実修正反映/記法露出0/markdown残骸0 |
| ⑩ | 仕上げ | 記事台帳（MEMORY.md）を ID・URL・公開日・要点で更新 ＋ 振り返りレポート ＋ 完了URLを `🔗` 付きで提示 |
| ⑪ | ローカルミラー同期（**2026-07-29追加・省略禁止**） | `publish_article.py` 経由の公開なら**自動実行される**（2026-08-01公開後フック）。WP側を `_request` 直叩きで直した場合は手動で `python3 blog/scripts/sync_posts_to_local.py`。**ここを飛ばすと手元の写しが古くなり、次の横断点検で誤った判断をする**（実際に原稿9本／公開13記事まで乖離した） |

| ⑬ | 内部リンク点検（推奨） | `python3 blog/scripts/suggest_internal_links.py --slug <slug>` で関連既存記事の上位候補を確認し、本文に自然な内部リンクを2〜3本置く（新記事→旧記事だけでなく、**旧記事側からも新記事へ**貼ると効果が高い） |

## 💰 アフィリエイト掲載の標準（`:::product` カード）── 2026-07-23 制定・全記事必須

**すべてのレビュー記事は、主役商品（と強く推す関連商品）を `:::product` スマートカードで掲載する。** DORIBIRU記事・MaGdget記事が正典。過去記事も順次この標準へ改修する。

### A. 掲載フォーマット：`:::product` カード
本文mdに以下を書くと、Amazon＋楽天が横並びのカード（オレンジ＝Amazon／赤＝楽天／青＝Yahoo）に変換される。実装は **`wp_block_builder.py`（本番）と `preview_server.py`（プレビュー）の両方**にあり、`image`は任意・各`amazon`/`rakuten`/`yahoo`は在るものだけボタン化される。

```
:::product
name: 商品名（★評価／件数 などの信頼シグナルを添えてよい）
image: <公式商品画像URL>
amazon: https://www.amazon.co.jp/dp/<ASIN>?tag=gp6sk1029-22
rakuten: <楽天アフィリURL（a.r10.to 短縮 or hb.afl フル）>
rakuten_label: 楽天市場で価格比較（検索・カテゴリーページへ送る場合だけ指定）
:::
```

- 置き場所：**結論／まとめ直後**に主役商品カードを1枚。加えて、本文中で強く言及した関連商品の近くにもインラインで置いてよい（DORIBIRU記事のMaGdget枠が例）。
- 素リンク（`[○○をAmazonで見る](...)`）だけで済ませない。主役商品は必ずカード化する。
- 商品ページへ送る通常カードは `rakuten_label` を省略して「楽天市場で購入」とする。検索・カテゴリーページへ送る横断比較リンクだけ「楽天市場で価格比較」と明示し、遷移先を誤認させない。

### B. Amazonリンク
- ASINを商品ページで特定 → `https://www.amazon.co.jp/dp/<ASIN>?tag=gp6sk1029-22`（アソシエイトID固定）。
- 純正がAmazonに無い消耗品は信頼ブランドで代替（ユーザー選択）。

### C. 楽天リンク生成（affiliate.rakuten.co.jp・Claude in Chrome）
> 💡 2026-08-01スキル化：起動語「**楽天リンク**」で以下の手順＋台帳確認＋バリエーション罠チェックまで一括実行（`.claude/skills/rakuten-link/`）。**必ず台帳（MEMORY.md）を先に見て、既存リンクは再生成しない。**
1. 楽天市場で対象商品を検索し、**商品ページURL**（`item.rakuten.co.jp/<shop>/<code>/`）を取得。**タイトル・価格がレビュー品と一致**するか確認。
2. `affiliate.rakuten.co.jp` 上部の「**URLを入力してリンクを作成**」に商品URLを入れて送信 → 「商品リンクを作成」画面へ。
3. リンクタイプで「**短縮URL**」を選ぶと `a.r10.to/xxxx` が得られる（クエリ無しなので `javascript_tool` で `textarea/input` の value を読み取れる）。「リンクのみ」の `hb.afl...` フルURLは**クエリを含むためJS読取がブロックされる**→短縮URLが安全確実。
4. 取得したURLを `rakuten:` に貼る。
- ⚠️ 自分のアフィリンクを自分でクリックしない（規約）。検証は生成元の商品一致確認で足りる。

### D. カード画像（**最重要の落とし穴**）
- 画像は**レビュー対象ASIN／商品と一致する公式商品画像**を使う。**Amazonのメイン画像を第一候補**にする（ASIN一致で誤りが起きにくい）。取得：Amazon商品ページの `#landingImage` の `data-old-hires` / `data-a-dynamic-image`。例 `https://m.media-amazon.com/images/I/xxxx._AC_SL1200_.jpg`。
- 🔴 **楽天の「公式メイン画像」はブランド共通の別商品画像のことがある**（実例：MaGdgetショルダーストラップの楽天メイン画像が別商品「Charge Ring」だった）。楽天画像を使うときは**必ず画像を表示して目視確認**。
- URL内の `+` は src ではそのまま有効（パス内の`+`は空白ではない）。差し替え後は**プレビューで `naturalWidth>0`** を確認。
- 詳細は memory `feedback_affiliate_card_image.md` 参照。

### D-2. カードは「冒頭」と「結論後」の2箇所に置く（2026-07-30制定）
- 🔴 **主役商品のカードは「急いでいる人へ（3行まとめ）」の直後にも置く**。結論後・まとめ前にしか無いと、**最後まで読まない読者には導線が存在しない**のと同じになる（2026-07-30の実測：12記事すべてで最初のカードが平均**76%地点**、冒頭25%以内は**0本**だった → 対応後は平均**16%**・冒頭30%以内が**10/12本**）。
- 冒頭カードの前に一言添える：「詳しい理由は本文で書きますが、**先に商品だけ確認したい方はこちらからどうぞ**」（急かさない・押し付けない）。
- 既存記事への一括適用：`python3 blog/scripts/add_top_product_card.py [--apply]`（まとめ直後に既にカードがある記事は自動スキップ）。
- 🔴 **冒頭にカードを置いたら、PR表記も必ずその前に置く**（次項E）。順序を逆にすると景表法上まずい。

### E. PR表記（景表法・ステマ規制対応・必須）
掲載した提供元をすべて明記する。標準文：
```
> ※本記事には広告（Amazonアソシエイト・楽天アフィリエイト）を含みます。リンク経由で購入いただくと、サイト運営者に紹介料が入る場合があります。価格は変わりません。
```
- Amazonのみの記事は「（Amazonアソシエイト）」、両方なら「（Amazonアソシエイト・楽天アフィリエイト）」と**実態に合わせる**。
- WP公開版はリンクに `rel="sponsored nofollow noopener"` が自動付与される。
- 🔴 **PR表記は「最初の広告リンクより前」に必ず置く（2026-07-30制定）**。ステマ規制は「広告と気づける状態で広告に触れさせる」ことを求めるため、**末尾にだけ書いてあっても不十分**。冒頭カードを入れたなら、その**直前**に簡潔版を置く（末尾の詳細版は残してよい・二重表示は問題ない）。
  - 一括適用：`python3 blog/scripts/add_top_pr_notice.py [--apply]`（楽天リンクの有無を見て文言を自動で出し分け・二重挿入は自動スキップ）
  - 点検：本文中で `ptgl-pr-top` の位置 < `ptgl-product-box` の位置 になっているか

### F. 公開前チェック（⑦ドライランに追加）
- プレビュー（`localhost:8794`）で **各カードの Amazon/楽天 ボタンの href と 画像表示（naturalWidth>0）** をE2E確認。
- PR表記が掲載実態（Amazon/楽天）と一致しているか。
- カードの `name` の商品名・価格・評価が最新か（④事実確認と整合）。

## クイックリファレンス（毎回必ず確認）
1. 金額換算セクション必須（全記事）
2. キャラ対話2〜3箇所（オオタニ所長 + タナカ）
3. WPブロックは wp_block_builder.py 経由（手書きHTML禁止）
4. 価格・スペックはメーカー公式で必ず裏取り
5. 投稿後URLを必ず出力（`🔗 https://...`）
6. **画像は必ず image_resizer.py で2000px以下に**（APIエラー防止）
7. **JIN:R装飾ルール**：最重要強調は `***xxx***`（水色アンダーライン自動付与）。`**xxx**` に数値・日付・単位を含むと自動で水色アンダーライン
7-b. 🔴 **強調の量を絞る（2026-07-27制定・スマホ可読性）**：**水色アンダーラインは「1段落につき最大1箇所」**。同じ段落で2つ目以降は太字（`**xxx**` で数値を含まない形）に留める。目安は**本文1,000字あたり3〜5箇所**（表・リスト内は別枠でOK）。**全部を強調すると何も目立たず、スマホでは「文字がいっぱい」に見える**。1段落に残す1つは「**いちばん価値の高い数字**（金額・倍率＞時間＞ただの数字）」を選ぶ。既存記事の間引きは `scratchpad/deemph.py <post_id>` の方式（本文テキストは1文字も変えず span だけ外す）
7-c. 🔴 **読者に偉そうな態度は絶対NG（2026-07-29制定）**：自信のある結論（ドヤ顔）は歓迎だが、**命令形・詰問・見下し・言い渡しは書かない**。読者に向けるセリフと地の文は敬体。**記事の冒頭を吹き出しで始めない**（挨拶→3行まとめ→吹き出しの順）。詳細は [skills/writing.md](skills/writing.md) §6・§16
7-d. 🔴🔴 **やっていない体験を書かせない（2026-07-29制定・最重要）**：AIは**使っていない機能の使用感を自然に創作する**。執筆指示には必ず「**先にヒアリングしてから書き始めて／ヒアリングした内容以外のことを予想で書かないこと**」を入れる。新製品・マイナー製品は自分から情報を与える。依頼文の定型は [skills/writing.md](skills/writing.md) §14-b
7-e. 📁 **記事のローカルミラーを最新に保つ（2026-07-29制定）**：`python3 blog/scripts/sync_posts_to_local.py` で全公開記事を `blog/posts/` に .md 同期する。**WP側を直したら必ず実行**。全記事の横断点検（価格の食い違い・口調・アフィリ漏れ）が grep 一発（0.01秒）で済み、文体の参照元にもなる

10. **レビューはアプリ内ブラウザを横に表示して行う**（2026-07-18制定）。ローカルプレビューを開いたら、画面を隠さずユーザーと同じ見た目を確認する

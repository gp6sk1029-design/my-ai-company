# アプリ・ツール開発 実戦プレイブック
# ── 記事めしPWAの改善で得た教訓を、全アプリ・ツール開発に使える形に一般化したもの ──

> 出所：記事めしPWA（blog/pwa-cloudflare + GAS）の連続改善（2026-07）で繰り返し効いた原則を抽出。
> **記事めしに限らず、PWA・Webツール・自動化スクリプト・GAS・Cloudflare Workers 等すべてに適用する。**
> 新しいアプリ/ツールを作る・直すときは、着手前にこの章に目を通す。ここで得た新しい教訓も追記して育てる。

## この文書の使い方（3行）
1. 新規開発・改修の**着手前**にA〜Eの原則を確認する。
2. 迷ったら「**壊さない・分離する・実測する・実機で確かめる**」に立ち返る。
3. 新しく効いた原則は末尾「追記ログ」に足し、汎用性が高ければ CLAUDE.md「標準パターン」へ昇格提案する。

## A. データの持ち方（壊さない・混ざらない設計）

### A-1. 複数の「作業対象」を扱うなら、全ローカル状態に“持ち主ID”を最初から付ける
- **原則**：1つのアプリが複数の対象（記事・案件・プロジェクト・ユーザー・タブ）を切り替えて扱うなら、**キュー・下書き・編集中フラグ・一時状態のすべて**に「どの対象のものか」を示すID（ownerId）を持たせる。
- **なぜ**：「切替時にクリアする」設計は、クリア漏れの経路が必ず残る（特に下記A-2）。「持ち主で分離する」設計なら、そもそも混ざりようがない。
- **やり方**：レコード生成時に `ownerId` を刻印 → 表示・送信・保存は「現在の対象＋未割り当てのみ」を対象にする。未選択で作ったものは、対象選択時に“引き取る”。
- 出所：記事めし「記事別データ分離」。前の記事の画像・メモが次の記事に混入・上書きされる事故を根絶。

### A-2. プログラムによる値の代入は change イベントを発火しない＝ガードの抜け穴
- **原則**：`select.value = x` のようなプログラム代入は `change` を発火しない。change ハンドラに置いた「混入防止ダイアログ」等は**素通り**される。
- **やり方**：プログラムで状態を変えたら、必要な後続処理（切替・再描画・保存）を**明示的に呼ぶ**か、共通の切替関数に集約して全経路をそこに通す。

### A-3. 誤上書きは「ブロック」より「新規保存に転換」— データを失わない方向に倒す
- **原則**：上書き先が本当に正しいと確認できないときは、操作を止めるだけでなく**新規保存に切り替える**。どちらのデータも失わない。
- 出所：再編集情報が残ったまま別対象で送信し、元データを破壊していた事故 → 「上書き先が現在の対象に実在しなければ新規保存」。

### A-4. ユーザー向けの「削除」は可逆（ゴミ箱）に倒し、確認文に「復元できる」と書く
- **原則**：完全削除ではなく**ゴミ箱（setTrashed / ソフトデリート）**。確認ダイアログに「◯日以内なら復元できます」と明記し、消える対象名も見せる。
- **なぜ**：破壊操作の心理的ハードルが下がり、誤操作時も救済できる。

### A-5. 保存は二層（ローカル即時＋サーバー権威）
- **原則**：①localStorage/IndexedDB に即時保存（オフライン耐性・切替やリロードで残る）②サーバー（Drive/DB）に保存（別端末・別日でも復元）。読込は「ローカル即時 → サーバーで上書き」の順。
- 出所：メモ・商品情報の記事別保存。「ローカル即時＋サーバー権威」の二層で、オフラインと端末跨ぎを両立。

### A-6. 上書き保存は「置換（setContent/update）」で。「削除→新規作成」は消失窓を作る
- **原則**：既存を消してから作り直す方式は、作成が失敗した瞬間にデータが丸ごと消える窓がある。**その場で中身だけ差し替える**（setContent / UPDATE）方が安全で、IDも変わらない。

### A-7. 重複判定・照合は「正しいスコープ」で行う
- **原則**：重複排除やキャッシュ照合は、対象単位（記事フォルダ単位など）に**スコープを限定**する。全体で照合すると「別対象で同じものが使えない／消えたように見える」事故になる。台帳・キャッシュは**実体が消えていないか（trashed/削除）も確認**する。

## B. UI/UX の落とし穴

### B-1. 機能の入口は「ユーザーが今いる画面」に置く
- **原則**：便利な機能でも、作業中の画面から呼べなければ“無い”のと同じ。**共有state＋ピッカー/呼び出し関数化**で、複数の画面から同じ機能を呼べるようにする。
- 出所：取り込んだ商品情報を「上部コーナー」だけに置いたら、編集中の別カードからは見えず「機能が出ない」と言われた → 共有化して各画面にボタン設置。

### B-2. グローバルなイベント横取り（paste / keydown 等）は「入力系要素を最初から除外」
- **原則**：`document` 全体で拾うイベントは、`input / textarea / select / contenteditable` を除外する。「便利だから全域で拾う」は、クリップボード等に何が残っているか次第で誤爆する。
- 出所：画像貼付の全体pasteリスナーが、入力欄への文字⌘Vまで横取りして別モーダルを出していた。

### B-3. CSS：`[hidden]` 属性は `display:flex/grid` に負ける
- **原則**：`.foo{display:flex}` があると `<div hidden>` が効かない（UAの `[hidden]{display:none}` に勝つ）。要素を隠す前提の場所は `.foo[hidden]{display:none!important}` を明示する。

### B-4. ボタンの文字は折り返さない・サイズを揃える
- **原則**：ボタン内テキストは `white-space:nowrap`。幅が足りないときは文字を折り返さず、ボタンごと次行へ回す。既定の大型スタイルに引きずられて1つだけ浮かないよう、同じバー/行のボタンはサイズを統一する。

### B-5. 選択の結果は「保持して見える化」する
- **原則**：ドロップダウン等で割り当てたら、選択を初期値に戻さず**保持**して「どこに入れたか」を見せる。完了は色（緑等）で示すと、やった／まだが一目で分かる。

## C. 外部連携・AI 活用

### C-1. 外部サービスの制限値は「推測せず実測」する
- **原則**：URL長・レート・サイズ等の上限は、`fetch(url, {credentials:'include'})` 等で**実際のステータスを計測**して確かめる（ページ遷移せずCookie込みで確認できる）。上限はCookie量などで変動するので、**実測値の8割**をマージンとして設計に採る。
- 出所：ChatGPTのURLプリフィル上限を実測（約6.1KBまでOK・6.3KBで431）→ 5000バイトを採用。

### C-2. 切り詰めは「先頭から」でなく「ユーザーが入力した情報を最優先」で
- **原則**：文字数制限で削るとき、定型文の先頭から取ると肝心のユーザー入力が枠外に落ちる。**入力値を先に載せ**、余った枠に定型文を足す。

### C-3. 二段渡し（URL＋クリップボード等）は、片方を変えたらもう片方の前提を確認
- **原則**：「主データはA、詳細はB」の二経路がある機能で片方の仕様を変えたら、もう片方が前提にしていた役割が崩れていないか必ず確認する。
- 出所：画像を単独クリップボードコピーに変えた際、「URLは要約・全文はクリップボード」という前提が崩れ、補足がAIに届かなくなった。

### C-4. AIへの指示は「集める情報源」＋「返す形式」を両方指定する
- **原則**：AIに調べさせる・生成させるときは、①**どこから集めるか**（EC/口コミ/公式/他ブログ 等）と ②**どの形で返すか**（固定ラベル・区切り記号・1行など）を両方書く。質と再利用性が安定する。
- **付随**：自前パーサで読み戻すなら、AIに「出典番号や `[ ]` 記号・太字を付けない」と指示し、装飾の混入を**発生源で抑制**する。

### C-5. AI画像編集等は「ブラウザ操作＝Claude in Chrome」を第一に、API課金は必要な時だけ
- **原則**（CLAUDE.md方針の再確認）：人がブラウザでできる作業（既存AIに貼って回答取得等）はAPI課金せずURL連携＋クリップボードで済ませる。エンドユーザー向け・バックグラウンド・大量処理のみAPI（Gemini等）。
- 出所：商品情報リサーチは「AIに貼る→貼り戻す」既存パターンの再利用でAPI課金ゼロで実現。

## D. 検証・デプロイ

### D-1. 構文チェックで満足しない。実機でE2E再現する
- **原則**：`node --check`（構文）はスタートライン。**実ブラウザで実際の操作フローを再現**し、状態・保存・表示を数値で確認してから完了とする。コンソールエラーゼロも確認。
- **手段**：ローカル静的サーバー＋Claude in Chrome で、テスト用データ（`__test__` 等）を使い、作った直後に自分で叩く。テストで作ったデータは必ず掃除する。

### D-2. デプロイ後の確認は「本番の実URL」で。キャッシュキーの違いに注意
- **原則**：反映確認は配信元の実URLで行う。Cloudflare Pages は `/` と `/index.html` でキャッシュキーが別 → HTMLはルート`/`で確認。エイリアス反映は最大30秒遅延。JSやCSSに“マーカー文字列”を仕込み `curl | grep` で反映を機械確認する。

### D-3. サーバー（GAS等）はURL不変で再デプロイできる手順を固定化する
- **原則**：バックエンドはエンドポイントURLを変えずに新バージョンを出せる手順を用意（GASなら `clasp push -f` → `clasp create-deployment -i <同じdeploymentId>`）。クライアント側の接続先URL更新が不要になる。疎通確認はGoogleのリダイレクトでPOST判定不能なので**GET系アクションで確認**。

## E. パーサ・データ整形

### E-1. 自前パーサは「ヘッダ/引用/装飾行」を除外し、区切りは1軸に統一
- **原則**：保存フォーマットを自前で読み戻すとき、`#`見出し・`>`引用・区切り線・`**`太字などの**非データ行を最初に除外**する。多値は「1軸の区切り（`/` 等）」に統一し、多行にしない（往復で壊れる）。
- 出所：保存ファイルの見出し行を項目として拾ってしまう／複数行メモが往復で消えるバグ。

### E-2. 「1項目=1行」を守れば往復で壊れない
- **原則**：保存→読込を繰り返すデータは「1件=1行」に正規化する。カテゴリごとに集約し、分解しすぎない（読みにくく、往復にも弱い）。

## 迷ったときの合言葉
- **壊さない**（可逆・非破壊・二層保存・置換保存）
- **分離する**（持ち主IDで混ぜない）
- **実測する**（外部制限は推測でなく計測）
- **実機で確かめる**（構文でなく再現テスト＋本番URL確認）
- **今いる場所に置く**（機能の入口はユーザーの手元に）

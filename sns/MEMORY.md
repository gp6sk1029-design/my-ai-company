### X（旧Twitter）
- 2026/08/22：ブログ記事1110（C26セレナのタイヤ交換総額比較）の公開後キューを初めて実運用。数字型2案を作成し、本文はX内完結、記事URLとPR表記は返信へ分離、アイキャッチv4を添付する形で `status: 原稿済み` にした。送信はユーザーが行う。
- 2026/08/22：文章1本＋画像1枚では訴求の根拠と注意点が伝わりきらないため、X下書きを「訴求分析＋本文＋返信＋4枚図解」の拡散セットへ拡張。記事1110では①15,920円差の実写フック ②75,600円対59,680円の同条件比較 ③楽天側の内訳 ④同一ショップ必須の注意を1200px正方形で生成した。投稿送信は引き続きユーザーが行う。
- 2026/08/23：ユーザーの文体調整で「タイヤより先に財布がパンク」「別ショップを混ぜるとカート内で事故」という商品テーマに沿った比喩を採用。数字の信頼性を保ったまま軽い笑いを加え、指定により関連タグを4個へ増やした。効果は投稿後3日の数値で確認する。
- 2026/08/23：ブログ流入が目的の投稿では、URLを返信だけに置くと導線が分かりにくいというユーザー指摘を反映。X公式では本文リンクが正式対応し、URLはt.coの23文字として数えられる。リンク位置を一律返信にせず、認知優先=`reply`／流入優先=`main`でキャンペーンごとに選ぶ方式へ変更した。
- 2026/08/23：プロフィール実測は5投稿・3フォロワー。再始動直後で、Premiumの月額より投稿・交流の母数不足がボトルネックと判断し、最初の30日または30投稿までは無料版を継続する。Basicは編集・長文が月2回以上必要になった場合、Premiumは青いチェック・Media Studio・クリエイター機能を実際に使う段階で再検討する。
- 2026/08/23：法令・楽天の最低基準では、PR表記を「アフィリエイト記事なら一律必須」とするのは過剰。消費者庁は自主投稿ならPR不要、楽天も通常成果報酬だけなら任意としている。ただし、この時点ではX独自ポリシーを未確認だったため、次項の横断調査でX上の運用を修正した。記事側の広告表示は従来どおり冒頭に置く。
- 2026/08/23：国内ガジェットブログ・X・YouTubeを横断調査し、法令・ASPとプラットフォーム規約を分けて判断する必要があると判明。Xはアフィリエイト報酬も有料パートナーシップに含め、ポスト内の商用表示を求めるため、自腹＋通常アフィリエイトでも `#PR` ではなく `※記事内にアフィリエイト広告を含みます` と同じ本文内に表示する。商品提供は `提供：会社名`、有償・指定投稿は `PR＋提供元`。YouTubeは提供元表示・概要欄のアフィリエイト表示・有料プロモーション設定を分離する。分析正本は `reports/2026-08-23_gadget-media-pr-affiliate-analysis.md`。
- 2026/08/24：公開済み13記事の未拡散解消を実施。DORIBIRU記事はユーザーが画像付きで投稿し、残り12記事はアイキャッチ画像・本文URL・必要なアフィリエイト表示を付けてXの未送信ポストへ保存した。実効文字数は全件140字以内。既存のタイヤ下書きは削除せず保持。Chrome拡張のファイル選択がローカル画像を拒否したが、ブラウザのクリップボードへJPEGを書き込み、本文欄へ貼り付ける方式で添付できた。保存後は全12記事IDと画像URLを未送信ポスト一覧で照合した。
- 2026/08/27：ROI計算ツール公開キャンペーンを作成。単なる機能紹介ではなく、①59,800円→約13か月の具体例 ②入力条件 ③時短・電気代・消耗品・維持費 ④3ステップ・非保存・共有機能の4枚で、数字の根拠と利用不安を順に解消した。第1弾本文はX換算120字、画像4枚付きで未送信ポストへ保存。1回で終わらせず、数字型→生産技術の裏話型→後悔防止・共有機能型の3投稿へ展開し、同一文面の連投を避ける。効果は各投稿3日後に検証する。

## SNS部門の開発履歴

### 🔴 2026/08/01：ブログ部門へ統合（CLAUDE.md v5.0）
- **決定**：SNSを独立部門から「コンテンツ部門（ブログ×SNS）の後工程」へ。独立セッションは通常起動せず、**記事を公開したセッション（役割キー `blog`）がそのまま拡散まで担当**する
- **根拠（実測）**：①SNS部門は5/2新設から約3ヶ月ゼロ稼働 ②12記事公開して拡散ゼロ ③X最終投稿は2025/8・フォロワー2（8/1実測）④SNS原稿の原料は記事の実測数字（価格・ROI）そのもので、別セッションだと文脈を毎回読み直す二重コストと事実誤りリスクが出る
- **決め手**：7/31に `publish_article.py` の公開後フックで**SNS原稿キューが自動生成される**ようになり、ツール側は既に統合済みだった。看板（モード・役割）だけが分かれている状態を実態に合わせた
- **変えたもの**：CLAUDE.md（4モード化・役割カタログ・1セッション1セクション規定・v5.0）／目次.md／blog・sns の SKILL.md 冒頭／handover.py（blog役割にSNSキーワード統合・sns は `DORMANT_ROLES` で自動推定から除外）
- **変えていないもの**：`sns/` フォルダ構成・チャネル別SKILL・calendar・queue運用は**そのまま**（中身は健全なので動かさない）。役割キー `sns` も温存（`--role sns` は今も使える）
- 🚫 **統合してもAIが投稿するわけではない**：リプ送信・投稿の最終送信は従来どおり人間（[channels/x/SKILL.md](channels/x/SKILL.md) §0-4のハイブリッド運用を厳守）
- **再分離の条件**：①Instagram／YouTubeの本格運用開始 ②SNS投稿が週5本超 ③SNS作業でセッション容量を恒常的に圧迫 ── いずれかに達したら `sns` 役割を復活させる（handover.py の `DORMANT_ROLES` から外す）
- **学び：部門を分けるかどうかは「業務量」で決める。量がないのに分けると、分割線がそのまま仕掛かりの滞留点になる**（未拡散記事12本がまさにそれ）
